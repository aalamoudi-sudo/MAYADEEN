# تحليل أداء صفحة الاستفسارات

## التشخيص اللاحق (سبتمبر 2026)

الإصلاح الأول أزال `inquiry_bootstrap` من المسار الحرج، لكنه لم يغيّر طريقة بناء
`inquiry_list` عند غياب cache الخادم. كان كل عنصر في القائمة يمر عبر
`inquirySerialize_`، وهذا بدوره يحمّل **كامل** تبويب `Inquiry Replies` وكامل تبويب
`Inquiry Reads` ليحسب `unread` والملخص. لذلك كانت كلفة الفتح البارد تنمو مع تاريخ
المحادثات، رغم أن القائمة لا تعرض أي رد. كذلك كان polling يطبق snapshot الواجهة
المخزن ثم استجابة الخادم في كل دورة، فيعيد بناء الجدول مرتين ويعيد المستخدم إلى
الصفحة الأولى حتى عندما لم تتغير البيانات.

الإصلاح الحالي يجعل `Inquiry Notifications` (الذي يُكتب أصلًا مع كل إنشاء/رد/تغيير)
مصدر حالة unread للقائمة والملخص. لم يعد `inquiry_list` يقرأ `Inquiry Replies` أو
`Inquiry Reads`؛ وتبقى الردود محمّلة عند فتح التفاصيل فقط وبصفحات من 100 سجل.
كما أصبحت الواجهة تقارن توقيع snapshot وتحتفظ بصفحة pagination الحالية ولا تمس DOM
إذا كانت نتيجة polling مطابقة.

### تحقق قابل لإعادة الإنتاج

في harness التكامل، مع استفسار واحد و3,000 رد تاريخي:

| القياس البارد | قبل | بعد |
|---|---:|---:|
| صفوف Sheets اللازمة لـ `inquiry_list` | 3,008 على الأقل (3,000 رد + بيانات القائمة) | 8 |
| قراءات `Inquiry Replies` | كامل التبويب | 0 |
| قراءات `Inquiry Reads` | كامل التبويب إذا احتوى بيانات | 0 |
| إعادة render عند snapshot مطابق | كانت تتم | 0 |

رقم «بعد» مقاس آليًا في `tests/inquiries.test.js` وليس تقديرًا. رقم «قبل» ناتج
مباشرة من مسار الكود السابق وعدد صفوف fixture نفسه؛ لا تتوفر في بيئة الاختبار
اعتمادات Apps Script المنشورة أو Google Sheets الإنتاجية، ولذلك لا يمكن تقديم زمن
شبكة/Apps Script حقيقي أو First UI/Data Visible بالميلي ثانية دون اختلاق أرقام.
عدادات `[inquiry_perf]` الموجودة في Apps Script (`duration_ms`, `rows_read`,
`sheet_reads`, وحجم الاستجابة) تبقى وسيلة القياس في النشر الحقيقي.

## ROOT CAUSE

كان مسار فتح الصفحة ينفذ طلبين إلى Apps Script **بالتتابع**: `inquiry_bootstrap` أولًا، ثم
`inquiry_list`. طلب bootstrap لا يلزم لعرض القائمة، لكنه يقرأ المستخدمين والمهام والإشعارات
ويحسب الملخص من جداول الاستفسارات والردود. لذلك كانت القائمة محجوبة خلف قراءة WBS والقراءات
المكررة من Google Sheets، ثم يعيد طلب القائمة حساب/جلب حالة القائمة مرة أخرى.

السبب الثاني كان أن كل رجوع إلى الصفحة يستدعي `inquiry_list` حتى لو كانت نفس هوية المستخدم
ونفس النطاق قد حُمّلا قبل ثوانٍ. كذلك كان `openInquiryScope` يستدعي `showPage` (الذي يحمّل
القائمة) ثم يستدعي التحميل مرة أخرى؛ كان الحارس يمنع التكرار فقط أثناء بقاء الطلب الأول قيد
التنفيذ، وليس بعد اكتماله.

أما DOM فليس السبب الرئيسي: القائمة ترسم 50 صفًا كحد أقصى، والتفاصيل تجلب آخر 100 رسالة.
ولا توجد assets أو صور خاصة بالصفحة، والـ polling مؤقت واحد كل 45 ثانية ويتوقف خارج الصفحة.

## الإصلاح والقياس البنيوي

| المسار | قبل | بعد |
|---|---:|---:|
| أول فتح للقائمة | طلبان متتابعان (`bootstrap` ثم `list`) | طلب `list` واحد |
| الرجوع خلال 45 ثانية لنفس النطاق | طلب `list` جديد | 0 طلبات؛ عرض snapshot فورًا |
| فتح نموذج إنشاء استفسار | bootstrap محمّل مسبقًا رغم عدم طلب النموذج | bootstrap كسول عند فتح النموذج فقط |
| أقصى صفوف DOM للقائمة | 50 | 50 (لم يتغير التصميم) |
| polling | مؤقت واحد / 45 ثانية | مؤقت واحد / 45 ثانية مع refresh صريح |

لم تُسجل أزمنة شبكة إنتاجية لأن المستودع لا يحتوي بيانات اعتماد لنشر Apps Script أو نسخة من
Google Sheet الإنتاجية. القياسات أعلاه هي عدد الطلبات ومسارات التنفيذ القابلة للإثبات بالاختبارات،
وليست تقديرات زمنية. حجم استجابة `inquiry_list` لم يتغير؛ أُضيف فقط علم `can_admin` صغير حتى لا
يحتاج عرض التبويب الإداري إلى bootstrap.

## سلامة البيانات

الـ cache في الواجهة معزول باسم المستخدم والنطاق، ومدته مساوية لدورة polling (45 ثانية).
عمليات الإنشاء والرد وتغيير الحالة وإعادة التوجيه وتسجيل رد متحقق منه تتجاوز الـ cache وتطلب
refresh موثوقًا. تسجيل الخروج يمسح cache والطلبات الجارية. يبقى CacheService ذو generation
على الخادم هو المرجع، ولا تتغير بنية Google Sheets أو الصلاحيات أو عقد الحقول القائمة.

## صيانة نموذج الإنشاء (سبتمبر 2026)

أكد تتبع النسخة السابقة أن تأخر زر «استفسار جديد» ليس مؤثر شبكة بصريًا فقط: الدالة
`openInquiryComposer` كانت تؤجل إنشاء الـ modal نفسه إلى ما بعد `inquiry_bootstrap` ومحاولته
حتى مرتين. وكان bootstrap يقرأ، فوق المستخدمين وWBS اللازمين، الملخص والإشعارات وجدول
الاستفسارات؛ وهي بيانات لا يحتاجها نموذج الإنشاء. لذلك لم يكن هناك أي feedback أو حقل قابل
للكتابة طوال زمن Apps Script وSheets والمحاولة الاحتياطية.

أصبح إطار النموذج يُرسم تزامنيًا عند الضغط، ويظل العنوان والتفاصيل قابلين للكتابة بينما تحمل
قائمتا المستلمين والمهام. الطلب الجاري مشترك، ولكل فتح generation وهوية جلسة تمنع استجابة
قديمة أو استجابة بعد الإغلاق من تعديل النموذج. تعرض الأخطاء وزر إعادة المحاولة داخل النموذج،
ولا يُفعّل الإرسال قبل جاهزية القوائم وصحة المستلم. كما أزيل حساب الملخص والإشعارات من bootstrap؛
بقي التحقق النهائي من المستلم والمهمة في `inquiryCreate_` على الخادم.

أضيفت مقاييس متصفح منفصلة `inquiry-composer-click-to-visible` و
`inquiry-composer-visible-to-ready`، وقياس `[inquiry_perf_client]` لكل استجابة خادم بحسب اسم
الإجراء فقط، من دون session token أو نص الاستفسار. ويستمر Apps Script بإصدار
`[inquiry_perf]` لزمن الخادم والقراءات. في harness المعزول صار bootstrap لا يقرأ أي صف بيانات
من Inquiries أو Notifications أو Replies أو Reads (تبقى قراءة headers الباردة للتحقق من
schema)، مقارنة بقراءته Inquiries وNotifications قبل الصيانة. لا تتوفر في المستودع جلسة نشر
أو Sheet إنتاجية، لذا لا توجد أرقام milliseconds فعلية قبل/بعد؛ ينبغي جمع المقاييس المسماة
أعلاه بعد النشر التجريبي وعدم تقديم زمن المحاكاة كزمن إنتاج.

عند فقد استجابة الإنشاء لا تمسح الواجهة المسودة ولا تعيد الكتابة تلقائيًا. تستعلم أولًا بواسطة
`inquiry_request_status` المقيد بالمستخدم ومعرف الطلب؛ وإذا لم توجد نتيجة فقط تتيح إعادة إرسال
نفس `request_id`. يظل منع التكرار النهائي في الخادم، كما هو للردود والإجراءات الأخرى.

## النشر والرجوع (لا يُنفّذ آليًا)

1. انشر `index.html` ونسخة Apps Script المبنية `apps-script/current-apps-script.gs` إلى بيئة
   تجريبية معزولة، ثم أنشئ deployment version جديدًا من دون تغيير Sheet أو خصائص المشاركة.
2. نفّذ smoke test بحسابات الصلاحيات الحالية ومن دون إرسال لمستخدمين حقيقيين، واجمع مقاييس
   Performance المذكورة وسجلات `[inquiry_perf]` المنزوعة من المحتوى الحساس.
3. بعد الموافقة، حدّث رابط الواجهة/نسخة Apps Script وفق إجراء النشر المعتاد. لا يتطلب التغيير
   migration أو تعديل headers أو صيغ Sheets.
4. للرجوع، أعد نشر deployment version السابق وأعد `index.html` السابق معًا؛ لا تحذف أي صفوف
   ولا تمسح cache يدويًا. الإجراء الجديد إضافي، لذلك لا يترك بيانات تحتاج rollback.

## مراجعة العقد والتوافق والقبول قبل الإنتاج

### مستهلكو bootstrap ومصدر العدادات

البحث الكامل في المصدر والاختبارات يبيّن أن الواجهة تستخدم بيانات bootstrap فقط في
`loadInquiryBootstrap` وخيارات المستلمين والمهام في composer. تفاصيل الإدارة تستمد قائمة
إعادة التوجيه من عقد `inquiry_detail` ولا تعتمد على bootstrap. أما `needs_reply` و
`new_replies` وشارة التنقل فتأتي الآن من `inquiry_list.summary` عند تحميل/تحديث القائمة، ومن
`inquiry_mark_read.summary` مباشرة بعد تسجيل القراءة. الإشعارات الخام لا يستهلكها كود الواجهة.

للتوافق الانتقالي بقي `inquiry_bootstrap` بعقده القديم كاملًا (`summary` و`notifications`)،
وأضيف `inquiry_composer_bootstrap` كمسار خفيف تستخدمه الواجهة الجديدة. إذا نُشرت الواجهة قبل
الخادم، تتراجع فقط عند خطأ `Unsupported inquiry action` إلى المسار القديم؛ ولا تتراجع عند خطأ
شبكة أو خادم آخر كي لا تضاعف الحمل. وبذلك يعمل ترتيب الخادم أولًا (المفضل) وكذلك الواجهة أولًا.
للرجوع يمكن إعادة أي طبقة منفردة؛ الواجهة القديمة تجد العقد القديم، والواجهة الجديدة تجد المسار
الخفيف أو fallback القديم.

### ما تغطيه الاختبارات السلوكية المعزولة

- فتح النموذج قبل اكتمال Promise الشبكة، النقر المتكرر، الإغلاق قبل الاستجابة، وفشل التحميل ثم
  إعادة المحاولة مع بقاء العنوان والتفاصيل.
- إنشاء عام ومرتبط بمهمة، أهلية المستلم والمهمة، وعزل التحقق من نتيجة الإنشاء بصاحب الطلب.
- حفظ إنشاء أو رد مع فقد الاستجابة ثم التحقق وإعادة نفس `request_id` من دون صف مكرر.
- نطاقات mine/assigned/all وصلاحية all، وتبديل تبويب الواجهة، والبحث وفلترة الحالة والأولوية
  وعرض الحالة الفارغة، وحدود pagination للقائمة ورسائل التفاصيل.
- فتح التفاصيل ومنع الاستجابة القديمة، تحميل الرسائل الأقدم، الرد، الرد مع «تمت الإجابة»، بدء
  المعالجة، الإغلاق، إعادة الفتح، وإعادة التوجيه، مع حالات السماح والمنع الخادمية.
- القراءة وحدود read cursor، unread والعدادات، cache invalidation، polling أثناء الكتابة، حفظ
  مسودة الرد، وفشل refresh مع بقاء آخر snapshot.

اختبارات regex/عقد المصدر تبقى منفصلة، وتغطي عدم ربط القائمة بـ bootstrap، توقف polling خارج
الصفحة، وجود الحراس ومعرفات الطلب، وتطابق bundle مع المصدر. لا تُعد هذه بديلًا عن الاختبارات
السلوكية المذكورة أو اختبار متصفح وخدمة حقيقية.

### قبول مختصر في بيئة اختبار قبل الإنتاج

1. انشر Apps Script أولًا في بيئة staging مع نسخة Sheet معزولة، ثم اختبر الواجهة القديمة للتأكد
   من بقاء `summary` و`notifications` والعدادات، وبعدها انشر الواجهة الجديدة.
2. على شبكة throttled افتح النموذج مرتين، اكتب أثناء التحميل، أغلقه قبل الاستجابة، ثم اختبر فشل
   bootstrap وإعادة المحاولة. كرر على شاشة ضيقة وتحقق من التركيز والتمرير وRTL.
3. بمحفظة حسابات اختبار فقط، نفّذ scopes الثلاثة، البحث والفلاتر، إنشاء عام ومرتبط بمهمة، الرد
   والحالات وإعادة التوجيه والقراءة، ثم بدّل الحساب أثناء طلب جارٍ.
4. حاكِ فقد استجابة POST بعد وصولها إلى الخادم، واضغط التحقق ثم أعد الإرسال؛ افحص Sheet للتأكد
   من وجود صف إنشاء/رد واحد فقط لنفس `request_id`.
5. اجمع `inquiry-composer-click-to-visible` و`inquiry-composer-visible-to-ready` و
   `[inquiry_perf_client]` و`[inquiry_perf]` للقائمة والتفاصيل، وقارنها بخط أساس staging.
6. لا تعتمد الصيانة على الإنتاج قبل نجاح هذه القائمة؛ لم يُنفذ هنا اختبار متصفح حقيقي أو اتصال
   بخدمة Apps Script/Sheets فعلية، ولذلك تبقى النتيجة مراجعة واختبارات معزولة وليست تأكيد إنتاج.
